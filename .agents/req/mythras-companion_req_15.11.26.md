# Mythras Companion — техническое задание для Hermes Agent

# 1. Назначение документа

Документ объединяет согласованные требования к доработкам существующего Mythras Tools / Mythras Companion (Angular-приложение).

1.  Адаптивная компоновка интерфейса.
2.  Исправление и визуализация локаций попаданий и повреждений.
3.  Поддержка Augmenting Skills при проверках навыков.
4.  Пересмотр отображения и расчёта параметров магических дисциплин.
5.  Поддержка нескольких теистических культов и отдельных Devotion Pool.
6.  Проверка совместимости, сохранения данных и корректности расчётов.

Это техническое задание для работы с существующим проектом, а не предложение переписать приложение с нуля. Документ предназначен для хранения в репозитории по пути `.agents/requirements/mythras-companion.md` и используется Hermes Agent, DeepSeek и другими агентами. Сам файл требований не является навыком (`SKILL.md`) и не загружается автоматически: агент открывает относящиеся к задаче разделы по указанию из корневого `AGENTS.md` или запроса пользователя.

# 3. Округление — только по правилам Mythras

Округление игровых величин должно соответствовать Mythras Core Rules; все производные величины рассчитываются по формулам книги.

Общее правило *Rounding of Numbers and Results*, Mythras Core Rules, Introduction, стр. 5: если при делении получается дробное число, результат **округляется вверх** до следующего целого (`Math.ceil()`), если специальное правило не задаёт другого способа. То же подтверждено авторами на форуме The Design Mechanism. В проверенных разделах Mythras Core Rules **не обнаружено универсальной категории вычислений с округлением вниз**. Не путать математическое округление с отдельными ограничениями, ступенями и таблицами правил.

| Ситуация                           | Правило и пример                                                              | Источник                                                 |
|------------------------------------|-------------------------------------------------------------------------------|----------------------------------------------------------|
| Critical Range                     | `ceil(значение_навыка_после_сложности / 10)`; 47% → 5                         | Core Rules, Skills, стр. 37–38                           |
| Augmenting Skills                  | 20% вспомогательного навыка; Locale 33% → +7                                  | Skills, стр. 50                                          |
| Начальные магические способности   | 1 за каждые **20% или неполные 20%**; 47% → 3                                 | Magic, стр. 118                                          |
| Профильная Folk Magic при создании | `ceil(FolkMagic / 10)`; 47% → 5                                               | Folk Magic, стр. 121                                     |
| Meditation                         | `ceil(Meditation / 10)`; 66% → 7                                              | Mysticism, стр. 154–155                                  |
| Максимальная Intensity таланта     | `ceil(Mysticism / 20)`; 34% → 2                                               | Mysticism, стр. 155                                      |
| Intensity Sorcery, Shaping Points  | `ceil(Invocation / 10)`, `ceil(Shaping / 10)`; Shaping 47% → 5                | Sorcery, стр. 161–162                                    |
| Intensity/Magnitude Theism         | `ceil(Devotion / 10)`                                                         | Theism, стр. 178, 182                                    |
| Лимиты по CHA/POW                  | Применять общее округление вверх при делении, если нет иного прямого указания | Animism, стр. 136; Mysticism, стр. 157; Theism, стр. 180 |
| Armour Penalty                     | Указано прямое округление вверх: `ceil(суммарный ENC / 5)`                    | Economics & Equipment, стр. 58                           |

**Приоритет вычисления:** явная формулировка из Core Rules и её примеры → общее правило округления книги → существующая протестированная реализация, если она не противоречит правилам. Если обнаруживается буквальное противоречие между фразой и примером, фиксировать оба и использовать проверенное книжное значение, не придумывая домашний вариант.

В разделе Augmenting Skills есть неточность формулировки: «twice its Critical range» при Locale 33% буквально дало бы +8, но книга прямо приводит **+7** и поясняет «20% of the skill». Для реализации использовать `ceil(augmentSkill * 0.2)` — так воспроизводится пример Core Rules. Не вычислять бонус как `2 * ceil(augmentSkill / 10)`.

Источники для сверки общей политики:

- [Mythras Core Rules — официальный фрагмент книги, стр. 5](https://d1vzi28wh99zvq.cloudfront.net/pdf_previews/191475-sample.pdf).
- [Mythras Imperative SRD, Introduction / Rounding](https://srd.mythras.net/).
- [Ответ одного из авторов правил на форуме The Design Mechanism](https://www.tapatalk.com/groups/designmechanism/mythras-core-rules-questions-t1825.html).

# 4. Адаптивность интерфейса

## 4.1. Целевые размеры экрана

Интерфейс должен корректно работать в трёх основных сценариях:

- Полноэкранное окно компьютера.
- Окно компьютера шириной около 960 px — типичный режим, когда приложение занимает половину экрана.
- Мобильное устройство.

Проверить как минимум следующие размеры:

| Сценарий                 | Размер тестового окна |
|:-------------------------|:----------------------|
| Десктоп, полный экран    | 1920 × 1080           |
| Десктоп, половина экрана | 960 × 1080            |
| Мобильный                | 390 × 844             |
| Мобильный, узкий         | 360 × 800             |

Размеры являются контрольными сценариями, а не требованием жёстко зафиксировать ширину компонентов.

## 4.2. Общие требования

- Перестроить компоновку так, чтобы она адаптировалась к доступной ширине.
- Уменьшить избыточные размеры карточек и внутренних отступов там, где это необходимо.
- Не растягивать блоки навыков на всю доступную ширину без необходимости.
- Не допускать переполнения, горизонтальной прокрутки всей страницы и наложения элементов.
- Сохранять читаемость названий, значений характеристик, навыков и атрибутов.
- Избегать резких скачков размеров при изменении ширины окна.
- Не ухудшать полноэкранную десктопную компоновку ради мобильной версии.

## 4.3. Мобильная версия

- Модель тела персонажа скрывать.
- Панель навыков по умолчанию скрывать.
- Панель навыков должна открываться как выдвижная панель слева.
- В панели навыков предусмотреть поиск.
- После выбора навыка панель должна позволять вернуться к основному экрану персонажа.
- Основная информация о персонаже должна оставаться доступной без постоянного отображения панели навыков.
- Управление не должно требовать точного попадания в слишком мелкие интерактивные элементы.

# 5. Локации попаданий и повреждения

## 5.1. Порядок локаций

Использовать следующий порядок отображения сверху вниз:

| Порядок | Локация                 | Диапазон броска 1d20 |
|--------:|:------------------------|---------------------:|
|       1 | Голова (Head)           |                19–20 |
|       2 | Левая рука (Left Arm)   |                16–18 |
|       3 | Правая рука (Right Arm) |                13–15 |
|       4 | Грудь (Chest)           |                10–12 |
|       5 | Живот (Abdomen)         |                  7–9 |
|       6 | Левая нога (Left Leg)   |                  4–6 |
|       7 | Правая нога (Right Leg) |                  1–3 |

Проверить существующее соответствие левой и правой сторон. Исправить перепутанные стороны в модели, подписях, диапазонах и обработчиках выбора. Лево и право должны соответствовать указанным названиям локаций, а не случайному расположению элементов на экране.

## 5.2. Выбор локации

Должны работать оба способа выбора:

1.  Нажатие на название локации в списке.
2.  Нажатие на соответствующую область модели тела.

Требования:

- Выбранная локация должна одинаково отображаться в списке и на модели.
- Выбор через список обновляет выделение на модели.
- Выбор через модель обновляет выделение в списке.
- Повторное нажатие на другую локацию переносит выделение.
- Состояние выделения должно быть единым, а не храниться независимо в двух компонентах.
- Если модель скрыта (например, на мобильном устройстве), выбор через список продолжает работать.

## 5.3. Отображение состояния локаций

Для каждой локации отображать отдельно:

- Текущие Hit Points (HP).
- Максимальные/базовые Hit Points согласно существующей модели персонажа.
- Armour Points (AP).
- Состояние повреждения, если оно применимо.

Не смешивать HP и AP: броня не должна визуально отображаться как здоровье.

## 5.4. Визуализация повреждений

Визуально различать:

- Обычную потерю HP.
- Отсечение/дисмембермент (Dismemberment).
- Дробление/разрушение локации (Crushing).
- Пронзение (Impaling).

Эти состояния должны отображаться отдельно от числового значения потерянных HP.

Не выводить отсечение, дробление или пронзение автоматически только из количества потерянных HP. Использовать существующие данные о типе ранения, специальных эффектах и состоянии локации. Если в модели данных нет нужного признака, сначала определить, где и как он должен храниться, не подменяя его эвристикой по HP.

Визуальные обозначения должны быть понятны и не перекрывать числовые показатели.

# 6. Проверки навыков и Augmenting Skills

## 6.1. Общая логика

Добавить возможность использовать один вспомогательный навык (Augmenting Skill) при проверке основного навыка.

- Для одной проверки можно выбрать не более одного вспомогательного навыка.
- Вспомогательный навык выбирается через поиск по названию.
- Поиск должен использовать существующий каталог навыков, включая пользовательские навыки, если они доступны в общей системе навыков.
- Нельзя выбрать основной навык в качестве собственного вспомогательного навыка.
- Не суммировать бонусы нескольких вспомогательных навыков.
- Выбранный вспомогательный навык должен быть виден в интерфейсе проверки.
- Пользователь должен иметь возможность убрать или заменить выбранный вспомогательный навык.

Пригодность вспомогательного навыка к конкретной ситуации определяется игроком/ведущим. Не пытаться автоматически определять семантическую уместность навыка по названию.

## 6.2. Расчёт бонуса по Mythras

Вспомогательный навык повышает шанс обычного успеха основного навыка на 20% своего текущего значения. Согласно примеру в Core Rules, стр. 50, Locale 33% даёт +7%.

- `augmentBonus = Math.ceil(augmentingSkillValue * 0.2)`.
- `augmentedSkill = primarySkillValue + augmentBonus`.
- Например, Locale 33% и основной навык 47% → +7 и 54% до применения сложности.
- Одновременно используется только один Augmenting Skill. Его выбор действует в рамках текущей проверки, не меняет сохранённый основной навык и не складывается с помощью другого персонажа.
- Применимость комбинации навыков зависит от ситуации и решения ведущего, а не только от имён навыков.
- Не обрезать значения навыков на 100%, поскольку в Mythras возможны значения выше 100%.

Указанное в книге «twice its Critical range» конфликтует с её же примером для 33%. Реализовать бонус в соответствии с пояснением «20% of the skill» и книжным результатом +7; см. раздел 3.

## 6.3. Сложность проверки

Окно сложностей должно показывать значение навыка и Critical Range для всех ступеней из Core Rules, Skills, стр. 38. Вычисления выполняются отдельно для обычной проверки и для проверки с одним Augmenting Skill.

| Ступень    | Множитель / правило |
|------------|---------------------|
| Automatic  | Бросок не требуется |
| Very Easy  | ×2                  |
| Easy       | ×1,5                |
| Standard   | ×1                  |
| Hard       | ×2/3                |
| Formidable | ×1/2                |
| Herculean  | ×1/10               |
| Hopeless   | Проверка невозможна |

Порядок для обычного порога успешности:

1.  Определить текущий основной навык `primarySkillValue` со всеми действующими обычными модификаторами персонажа.
2.  Если выбран вспомогательный навык, прибавить `ceil(augmentingSkillValue * 0.2)`.
3.  Применить множитель сложности к полученному значению.
4.  Если результат дробный, округлить вверх согласно общему правилу Mythras.

Например, основной навык 40%, вспомогательный 33% → +7; Hard: `ceil(47 × 2/3) = 32%`.

Для Automatic и Hopeless не вычислять диапазон броска как обычную проверку. Не заменять систему множителей альтернативной упрощённой таблицей фиксированных бонусов.

## 6.4. Critical Range и Fumble — вопрос разрешён правилами

**Правило прямо сформулировано в Core Rules, Skills, стр. 37:** Critical Range равен одной десятой **значения навыка, уже изменённого модификатором сложности**; дроби округляются вверх. Следовательно, Critical Range рассчитывается **после применения степени сложности**, а не до неё.

При использовании **Augmenting Skill** действует специальное исключение из Skills, стр. 50: бонус увеличивает обычный шанс успеха, **но не Critical Range и не Fumble Range** основного навыка.

Рассчитывать:

- `ordinaryTarget = ceil((primarySkillValue + augmentBonus) * difficultyMultiplier)`.
- `criticalTarget = ceil((primarySkillValue * difficultyMultiplier) / 10)` — **без** `augmentBonus`.
- `fumbleTarget`: диапазон 99–00, но при значении основного навыка **с учётом сложности и без augmentation** выше 100% — только 00. При использовании Augmenting Skill сам бонус вспомогательного навыка не должен менять Fumble Range.

Общие ограничения броска: 01–05 всегда успех; 96–00 всегда провал. Даже если порог навыка выше 100%, эти ограничения сохраняются. Если значение Critical Range численно выходит за доступный диапазон бросков, правила автоматического провала всё равно имеют приоритет.

Контрольный пример с основным навыком 40%, без augmentation:

| Сложность  | Порог обычного успеха | Critical Range |
|------------|----------------------:|---------------:|
| Very Easy  |                   80% |              8 |
| Easy       |                   60% |              6 |
| Standard   |                   40% |              4 |
| Hard       |                   27% |              3 |
| Formidable |                   20% |              2 |
| Herculean  |                    4% |              1 |

Если добавить вспомогательный навык 33%, обычный порог для Standard вырастет до 47%, а **Critical Range останется 4**. Для Hard обычный порог составит 32%, а **Critical Range останется 3**.

Расчёт Critical Range при изменении сложности установлен правилами; использовать указанную формулу и покрыть её тестами.

# 7. Культы, членство и магические традиции

## 7.1. Разделение понятий

Не объединять следующие сущности:

- Культ/организация — социальная и институциональная структура.
- Членство персонажа в культе — конкретная связь персонажа с организацией и его ранг.
- Магическая дисциплина — система сверхъестественных способностей.
- Традиция/школа/путь — конкретный источник знаний внутри дисциплины.
- Магический навык — навык, относящийся к конкретной дисциплине и, где это требуется правилами, к конкретной традиции.
- Изученные способности — заклинания, чудеса, духи или таланты, доступные персонажу.

Культ не обязательно является теистическим. Не следует автоматически присваивать каждому культу Devotion, Exhort или чудеса.

Один культ может быть связан с несколькими дисциплинами, если это допускается моделью кампании. Не следует жёстко связывать один культ с одной магической дисциплиной.

## 7.2. Несколько культов и существующие ранги

- Использовать **существующую** систему культов, рангов и их выбора в билдере (страница выбора культа), а не создавать новую универсальную таблицу рангов или параллельный справочник.
- Не менять существующее поведение рангов и ограничения вступления/продвижения без конкретного требования.
- Персонаж может принадлежать нескольким теистическим культам, если это разрешено игровым миром и правилами.
- Дополнительное требование в рамках этой задачи — отдельный Devotion Pool для каждого **теистического** культа с сохранением текущего/максимального значения, привязанный к существующей записи членства.
- Добавление второго культа не удаляет первый. Изменение ранга одного культа не меняет ранг другого.
- Не вводить автоматическую проверку антагонизма культов и не переделывать механизм выбора ранга.

# 8. Devotion Pool теистических культов

Devotion Pool — механика дисциплины Theism. Она применяется к теистическим культам и не должна переноситься на другие виды организаций или магические дисциплины.

## 8.1. Несколько теистических культов

Правила Mythras допускают членство персонажа в нескольких теистических культах при соблюдении условий совместимости культов.

- Каждый теистический культ имеет собственный Devotion Pool.
- У каждого культа отдельно хранятся ранг, Devotion, Exhort, текущий запас и максимальная вместимость Devotion Pool.
- Пулы разных культов не объединяются в один ресурс.
- Изменение запаса одного пула не должно напрямую изменять запас другого.
- Суммарное количество очков во всех теистических Devotion Pool не может превышать POW персонажа.
- Обычные личные Magic Points персонажа хранятся отдельно от Devotion Pool.

При пополнении Core Rules рекомендуют ограничивать текущий запас размером последнего пожертвования. Это рекомендация правил; не превращать её в дополнительное жёсткое ограничение без необходимости.

## 8.2. Максимальная вместимость

| Ранг        | Максимальный Devotion Pool |
|-------------|---------------------------:|
| Lay Member  |                          0 |
| Initiate    |            `ceil(POW / 4)` |
| Acolyte     |            `ceil(POW / 2)` |
| Priest      |        `ceil(3 * POW / 4)` |
| High Priest |                      `POW` |

Применять общее правило округления Mythras: если результат деления дробный, округлять вверх.

## 8.3. Стоимость и время обращения к божеству

| Ранг чуда | Стоимость | Время обращения |
|-----------|----------:|----------------:|
| Initiate  |      1 MP |           1 ход |
| Acolyte   |      2 MP |          2 хода |
| Priest    |      3 MP |          3 хода |

Результаты Exhort:

- Critical Success: чудо происходит бесплатно.
- Success: расходуется полная стоимость.
- Failure: чудо не происходит, очки не расходуются.
- Fumble: чудо не происходит, теряется 1 MP.

Magnitude и Intensity чуда определяются навыком Devotion:

`Intensity = Magnitude = ceil(Devotion / 10)`

Эти правила относятся только к Theism.

# 9. Магические дисциплины: требования к отображению и расчётам

Общие требования:

- Отображать только параметры, относящиеся к выбранной дисциплине.
- Разделять исходные навыки и вычисляемые показатели.
- Пересчитывать зависимые значения при изменении характеристик, навыков и рангов.
- Не дублировать один и тот же ресурс в нескольких дисциплинах.
- Не рассчитывать стоимость каждого отдельного заклинания, чуда или таланта в рамках этой задачи.
- Вместо индивидуального калькулятора стоимости показывать справочные правила стоимости и применения дисциплины.
- Не менять сами описания заклинаний, чудес, духов и талантов без отдельной задачи.

## 9.1. Folk Magic

Основная механика:

- Один общий навык Folk Magic применяется ко всем известным заклинаниям персонажа.
- Заклинания не имеют индивидуальных значений навыка.
- Базовые Intensity и Magnitude равны 1.
- Время применения — 1 ход.
- Обычная стоимость успешного применения — 1 MP.

Результат проверки:

| Результат        | Эффект                 | Расход MP |
|:-----------------|:-----------------------|----------:|
| Critical Success | Заклинание срабатывает |         0 |
| Success          | Заклинание срабатывает |         1 |
| Failure          | Не срабатывает         |         1 |
| Fumble           | Не срабатывает         |       1d3 |

Количество известных заклинаний не имеет общего верхнего лимита, если ведущий разрешает изучать новые заклинания.

Начальное количество:

- Для обычных персонажей: одно заклинание за каждые 20% навыка или неполные 20%; `ceil(FolkMagic / 20)` (кроме специальных правил профессий).
- Для профессий, специально связанных с Folk Magic: количество заклинаний равно одной десятой Folk Magic; `ceil(FolkMagic / 10)` по общему правилу.

Отображать:

- Значение навыка Folk Magic.
- Список известных заклинаний.
- Количество известных заклинаний.
- Базовые Intensity и Magnitude.
- Справку по времени и стоимости применения.

## 9.2. Animism

Основные навыки:

- Trance.
- Binding.

Trance:

- Позволяет обнаруживать духов в радиусе, равном POW персонажа в метрах.
- Для непосредственного взаимодействия с миром духов требуется 1 MP.
- Возможности Trance зависят от ранга традиции.

Основные возможности по рангам:

| Ранг              | Возможности                                                                                                |
|:------------------|:-----------------------------------------------------------------------------------------------------------|
| Follower          | Наблюдать и идентифицировать духов                                                                         |
| Spirit Worshipper | Общаться с духами                                                                                          |
| Shaman            | Проецировать душу в мир духов; притягивать духа в материальный мир или изгонять духа, овладевшего смертным |
| High Shaman       | Переносить души других людей в мир духов вместе с собой                                                    |

Время подготовки зависит от ранга и конкретного действия. Если приложение показывает эти возможности, использовать таблицу Trance Preparation Time из Core Rules, не заменяя её универсальным временем.

Binding:

- Максимальный POW духа, которого можно принудить, связать или контролировать, равен трём Critical Range навыка Binding.
- Critical Range по Mythras округляется вверх.
- Формула: `maxSpiritPOW = 3 * ceil(Binding / 10)`.

Количество духов в подчинении зависит от ранга:

| Ранг              | Максимальное количество |
|:------------------|------------------------:|
| Follower          |         `ceil(CHA / 4)` |
| Spirit Worshipper |         `ceil(CHA / 2)` |
| Shaman            |     `ceil(3 * CHA / 4)` |
| High Shaman       |                   `CHA` |

Не путать связанных духов с духами-союзниками, с которыми заключён договор. Лимит связан с духами, находящимися в подчинении.

Spirit Intensity определяется по POW духа:

|                Intensity |                POW |
|-------------------------:|-------------------:|
|                        0 |                1–6 |
|                        1 |               7–12 |
|                        2 |              13–18 |
|                        3 |              19–24 |
|                        4 |              25–30 |
|                        5 |              31–36 |
| Каждая следующая ступень | +6 к диапазону POW |

Spirit Damage анимиста определяется значением Binding:

| Binding | Spirit Damage                            |
|--------:|:-----------------------------------------|
|   01–20 | 1d2                                      |
|   21–40 | 1d4                                      |
|   41–60 | 1d6                                      |
|   61–80 | 1d8                                      |
|  81–100 | 1d10                                     |
| 101–120 | 2d6                                      |
| 121–140 | 1d8 + 1d6                                |
| 141–160 | 2d8                                      |
| 161–180 | 1d10 + 1d8                               |
| 181–200 | 2d10                                     |
| 201–220 | 2d10 + 1d2                               |
| 221–240 | 2d10 + 1d4                               |
| 241–260 | 2d10 + 1d6                               |
| 261–280 | 2d10 + 1d8                               |
| 281–300 | 3d10                                     |
|   Далее | Продолжать прогрессию таблицы Core Rules |

Для духов также учитывать, что их Intensity определяется их собственным POW, а не навыком анимиста.

Отображать:

- Trance и Binding.
- Радиус обнаружения духов.
- Максимальный POW духа, доступного для подчинения.
- Максимальное количество связанных духов по рангу и CHA.
- Spirit Damage.
- Таблицу/справку Spirit Intensity.
- Доступные возможности Trance по рангу.

Не создавать автоматическую систему поиска, переговоров, связывания и управления духами в рамках этой задачи, если она не существует в текущем проекте. Здесь требуется корректное отображение параметров и правил.

## 9.3. Mysticism

Основные навыки:

- Meditation — общий навык концентрации.
- Mysticism — отдельный навык для каждого мистического пути.

Путь (Path) содержит набор талантов. Один персонаж может изучать несколько путей, если это разрешено кампанией.

Типы талантов:

- Augment Skill.
- Invoke Trait.
- Enhance Attribute.

Ограничения:

| Показатель                                                | Формула проекта         |
|:----------------------------------------------------------|:------------------------|
| Максимальная Intensity одного таланта                     | `ceil(Mysticism / 20)`  |
| Максимальная суммарная Intensity действующих талантов     | `ceil(Meditation / 10)` |
| Максимальное количество одновременно тренируемых талантов | `ceil(POW / 2)`         |

Ограничение отдельного таланта рассчитывается по навыку Mysticism соответствующего пути.

Суммарная Intensity активных талантов ограничивается Meditation персонажа, а не суммой Mysticism всех путей.

Количество одновременно тренируемых талантов ограничивается половиной POW персонажа. Учитывать таланты всех путей совместно.

При смене регулярно тренируемых талантов правила предусматривают неделю практики и проверку Meditation. Отображать это в справке, если соответствующий процесс уже реализован.

Отображать:

- Список мистических путей персонажа.
- Отдельное значение Mysticism для каждого пути.
- Список талантов каждого пути.
- Максимальную Intensity отдельного таланта.
- Текущую суммарную Intensity активных талантов.
- Максимально допустимую суммарную Intensity.
- Количество тренируемых талантов и допустимый максимум.

Не рассчитывать стоимость каждого отдельного таланта в рамках этой задачи.

## 9.4. Sorcery

Основные навыки:

- Invocation — отдельный навык для каждого источника/школы колдовства.
- Shaping — существующий общий навык для формирования заклинаний. Не расширять модель ради дополнительных/альтернативных Shaping-компонентов.

Intensity заклинания:

`Intensity = ceil(Invocation / 10)`

Максимальное количество Shaping Points:

`ShapingPoints = ceil(Shaping / 10)`

По умолчанию Shaping управляет следующими компонентами:

- Combine.
- Duration.
- Magnitude.
- Range.
- Targets.

В рамках данной доработки использовать только пять базовых компонентов из таблицы Core Rules. **Дополнительные/альтернативные Shaping-компоненты не реализовывать и не включать в требования.**

Magnitude:

- Базовая Magnitude равна 1.
- Shaping Points, вложенные в Magnitude, увеличивают Magnitude.
- Shaping не изменяет Intensity.

Другие базовые параметры:

- Duration по умолчанию равна POW минут.
- Range по умолчанию — Touch.
- Target по умолчанию — одна цель.
- Дополнительные параметры определяются распределением Shaping Points по таблице Shaping.

Ограничения:

- Максимальное количество заклинаний, которые sorcerer может держать в памяти, равно INT.
- Количество одновременно поддерживаемых заклинаний не ограничено отдельным числом.
- Одновременно можно концентрироваться только на одном заклинании с Concentration.
- Длительные заклинания временно уменьшают доступный запас Magic Points на стоимость поддерживаемого эффекта до его окончания или прекращения.

Стоимость применения в справке:

`BaseCost = 1 + numberOfModifiedComponents + numberOfAdditionalCombinedSpells`

При Critical Success расходуется половина стоимости; при Success — полная стоимость; при Failure — 0; при Fumble — полная стоимость. Если при делении стоимости пополам получается дробный результат, применять общее правило округления Mythras (вверх), если иное не установлено конкретным правилом; автоматический расчёт стоимости отдельных заклинаний не требуется.

Отображать:

- Список школ/источников.
- Отдельный Invocation каждой школы.
- Shaping.
- Intensity.
- Максимальное количество Shaping Points.
- Базовую Magnitude.
- Максимальное количество запоминаемых заклинаний по INT.
- Текущее количество запомненных заклинаний.
- Ограничение на одно Concentration-заклинание.
- Справку по Shaping и стоимости.

Не создавать автоматический калькулятор стоимости каждого заклинания в рамках этой задачи.

## 9.5. Theism

Theism остаётся отдельной дисциплиной и использует стандартные правила Mythras Core Rules.

Основные навыки:

- Devotion — привязан к конкретному божеству, группе божеств или пантеону.
- Exhort — навык обращения к соответствующему божеству.

Intensity и Magnitude чудес:

`Intensity = Magnitude = ceil(Devotion / 10)`

Devotion Pool:

- Отдельный пул для каждого теистического культа.
- Общая сумма Magic Points во всех теистических пулах не должна превышать POW персонажа.
- Максимальная вместимость отдельного пула определяется рангом по таблице раздела 8.2.
- Обычные личные Magic Points персонажа хранятся отдельно от Devotion Pool.

Стоимость и время обращения:

| Ранг чуда | Стоимость |  Время |
|:----------|----------:|-------:|
| Initiate  |      1 MP |  1 ход |
| Acolyte   |      2 MP | 2 хода |
| Priest    |      3 MP | 3 хода |

Результаты Exhort и особенности пополнения пула приведены в разделе 8.3.

Отображать:

- Теистические культы персонажа.
- Отдельный Devotion для каждого соответствующего божества/культа.
- Exhort для соответствующего источника чудес.
- Ранг каждого культа.
- Текущий и максимальный Devotion Pool.
- Суммарное количество Magic Points во всех теистических пулах.
- Оставшуюся вместимость по общему лимиту POW.
- Intensity/Magnitude.
- Справку по стоимости и времени обращения.

Эти правила применять только к теистическим культам.

# 12. Критерии завершения

Работа считается выполненной, когда:

- Округления соответствуют Core Rules.
- Существующие персонажи и пользовательский контент сохраняются и корректно загружаются.

- Проект успешно собирается.

# 13. Границы задания и переиспользование существующей логики

- **Critical Range при сложности:** правило определено Core Rules, см. раздел 6.4; реализовать без отложения и без придумывания альтернативной формулы.
- **Shaping:** только пять основных компонентов (Combine, Duration, Magnitude, Range, Targets); дополнительные компоненты и их конфигурацию не реализовывать.
- **Ранги культов:** механизм уже существует в конструкторе; переиспользовать его, не создавать новую универсальную таблицу рангов и не перестраивать выбор ранга.
- **Стоимость магии:** предоставить справочную информацию по дисциплинам; не менять хранилище каждого заклинания ради индивидуального расчёта стоимости.
- **Остальные вопросы:** только при фактическом отсутствии правила в Core Rules и данных в существующей модели — сообщить конкретный пробел, не вводить новую механику.
